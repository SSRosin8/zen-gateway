# 开发流程

仓库根目录的 `AGENTS.md` 是开发纪律唯一来源。需求见 `docs/requirements.md`，架构见
`docs/architecture.md`，操作和配置示例见 `docs/usage.md`。

## 开始任务

1. 检查分支与工作树。新任务创建描述用途的功能分支；继续任务使用已有功能分支。
2. 保留用户未提交修改，不直接在主分支开发，不因换分支丢弃工作。
3. 读取相关实现、调用点、schema 与测试，先确认真实需求和边界。
4. 查找已有单一真相，例如 `ConfigSchema`、`isUsable`、`credentialFingerprint`，
   复用它们而不是复制逻辑（纪律 #4）。

## 实现和验证

- 从用户入口验证，不以“有函数、有单测”代替功能接通（纪律 #9）。
- 关键守卫写好后临时改坏实现，确认对应测试失败，再恢复实现（纪律 #1/#2）。
- 变异存活先区分路径不存在、输入集为空、其他条件掩盖和死信息，不默认加测试。
- 测试失败时先判断契约、实现和断言哪一方错误，不通过改预期掩盖回归（纪律 #3）。
- 文档只描述当前可用入口；配置示例要过 `ConfigSchema`，命令不能依赖个人配置。
- 修改功能时同步 requirements、architecture、usage 和相关 skill，移除旧说明。

```bash
npm run validate
```

完整关卡包括敏感文件检查、类型检查、双构建和全部测试，不能用局部测试代替。
构建必须在测试前；`tests/integration/service.test.ts` 会启动构建后的服务入口。
`src/shared/` 同时服务浏览器和 Node，不能引入 `node:*`。

## 提交与合入

1. 完成所有修改和完整验证，检查 diff 与敏感文件结果。
2. 按授权本地提交，记录改动原因、测试范围、变异结果和剩余限制。
3. 需要合入且已获授权时再申请 MR；未通过验证不得申请。

本地提交不自动包含推送、合并或改写历史授权。Git 身份使用仓库本地配置，不改全局。
禁止提交运行数据、环境文件、日志、备份、数据库、证书、私钥和真实凭证。
不要为了行数拆文件，是否拆分取决于当前职责边界与调用关系（纪律 #11）。
