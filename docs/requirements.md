# zen-gateway 需求说明

## 1. 文档目的

本文档描述当前 `zen-gateway` 的产品边界、配置约定、使用流程和可验收行为。它面向维护者和实际使用者，内容以当前代码、管理 API、管理后台和命令行脚本为准。

项目是一个供单个用户在本机运行的 Zen 网关。它把兼容的客户端请求转发到 Zen 上游，并在本机完成免费模型判定、Worker 调度、出口代理选择、流式透传、失败重试和运行统计。

## 2. 产品目标

- 在本机提供一个只监听回环地址的网关服务。
- 让兼容 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages 形状的客户端使用同一个本地入口。
- 只允许符合本地免费模型规则的请求进入上游，尽量避免把付费模型请求发出去。
- 支持多个 Worker，并把每个 Worker 的认证信息、出口绑定和运行期状态分开管理。
- 通过配置的公网出口发送请求，并按 IP 回显目标的实测公网 IP 判断多个 Worker 是否
  在该目标上共用出口（[测量范围](usage.md#回显-ip-的测量范围)）。
- 在上游失败时按错误类别选择候选 Worker 和重试策略，在客户端仍能获得清晰的错误形状。
- 原样转发客户端请求体和上游响应字节；网关只解析副本做判定和旁路统计。
- 提供一个仅回环可访问的管理 API，以及一个独立运行的 React 管理后台。
- 让配置错误、目录不可达、Worker 冷却、Clash 控制面故障和出口未探测等问题可以被定位。

## 3. 非目标与明确限制

- 不做多用户、租户、权限角色或远程管理。管理 API 只接受本机回环连接。
- 不把网关做成通用 provider 抽象；当前上游固定为 Zen，配置中的 `baseUrl` 只是该上游入口的地址。
- 不在网关进程中托管管理后台静态文件。服务端提供 API 和转发，管理后台由 Vite 开发服务器单独运行；需要生产静态托管时由外部静态服务器承担。
- 不把请求体转换成另一种协议格式。三个协议面分别对应 Zen 的原生端点，网关只做判定、补头和原样转发。
- 不根据模型目录自动推断价格，也不能自动发现新的“无后缀免费模型”；这类模型需要手工加入 `models.extraFreeIds`。
- 不保证匿名 Worker 一定能被 Zen 上游接受。匿名模式表示网关不发送 Worker 认证头，最终是否允许由上游决定。
- 不在每条转发请求中自动探活或自动切换 Clash 内核。Clash 的 `manual`/`auto` 选择、探活和批量探测各有明确入口。
- 不在管理后台直接编辑所有配置资源。当前后台可编辑 Worker、部分网关设置和部分模型规则；代理、Clash 内核和订阅的完整增删改仍需配置文件或 `setup` 流程。
- 不承诺把所有运行期状态写入配置文件。冷却、亲和、统计和批量探测进度由服务进程或运行时数据库保存。

## 4. 术语

| 术语 | 含义 |
| --- | --- |
| 网关 | 本项目的本机 HTTP 服务，监听 `127.0.0.1`，负责管理 API、模型目录和转发面。 |
| Relay Token | 客户端访问 `/v1/*` 转发面的本机凭证。它与 Zen API key 不同。 |
| Worker | 一组 Zen 身份与出口绑定。认证 Worker 携带 API key；匿名 Worker 不携带 key。 |
| 代理 | Worker 使用的网络出口配置，可以是直连协议，也可以经本机 Clash 桥接。 |
| Clash 内核 | 本机 Clash/mihomo 的 External Controller 及其本地混合代理端口。 |
| 协议面 | 一个客户端请求形状及其对应的上游路径：`chat`、`responses` 或 `messages`。 |
| 目录 | 从上游 `/models` 拉取并校验后的模型列表缓存。 |
| 免费判定 | `(freeSuffix 命中 ∪ extraFreeIds) ∩ 在架目录`；目录不可用时会标记为未核验。 |
| 回显出口独立性 | 按 IP 回显目标的实测公网 IP 分组，判断 Worker 访问该目标时是否共用出口。未探测不等于独立；与 Zen 实际出口的关系见 [测量范围](usage.md#回显-ip-的测量范围)。 |
| 亲和 | 会话或 Responses 指针与实际承接 Worker 的绑定，用于保持上游连续性。 |
| 批量探测 | 服务端持有进度的出口筛选与公网 IP 实测任务，同一时间只允许一批。 |

## 5. 运行形态

### 5.1 服务与端口

- `npm start` 先构建服务和后台，再启动网关并等待 `/health`。
- `npm run restart` 与 `start` 使用同样的构建和健康等待流程。
- 端口按 `ZG_PORT`、配置中的 `gateway.port`、默认值的优先级解析；服务端、启停脚本和 Vite 代理使用同一解析逻辑。
- 网关只监听回环地址。管理 API 和转发 API 不对局域网或公网开放。
- `npm stop` 或 SIGTERM/SIGINT 触发优雅关闭：停止接收新请求，有界等待在途请求，再关闭出口连接池和数据库。
- `ZG_DATA_DIR` 可把 `config.json`、日志、状态文件和运行时数据库移到其他数据目录。

### 5.2 管理后台

- `npm run dev` 启动 Vite 管理后台，默认开发端口为 5173。
- Vite 只代理 `/health` 和 `/api` 到网关；转发请求应直接访问网关的 `/v1/*`，不能把 `/v1` 当作 Vite 代理路径。
- 页面和列表筛选状态写入 URL hash；用量时间范围和未提交表单只保留在当前页面内存中。
- 网关不会把已构建的后台静态资源自动伺服出来，网关端口 `GET /` 返回 404。

## 6. 配置要求

配置文件默认位于数据目录的 `config.json`，由 `ConfigSchema` 严格校验。字段拼写错误、重复 id、跨资源引用错误和桥接矛盾都必须在加载或写入时失败。

### 6.1 网关

`gateway` 至少包含：

- `port`：监听端口。
- `baseUrl`：Zen 上游基础 URL，只接受 `http`/`https`，不得在 URL 中嵌入凭证。
- `relayToken`：客户端访问转发面的凭证，必须为足够长度的 URL-safe 字符串。
- `headersTimeoutMs`、`bodyTimeoutMs`：响应头等待和响应体空闲超时。
- `maxAttempts`：一条客户端请求最多尝试的 Worker 数。
- `directEgressIp`：本机直连出口最近一次实测的公网 IP，尚未探测时为 `null`。

### 6.2 Worker

每个 Worker 有唯一 `id`，并包含 `kind`、`name`、`enabled`、`proxyId` 和 `apiKey`：

- `authenticated` Worker 必须有非空 API key。
- `anonymous` Worker 的 key 在配置归一化时清空；网关不会为它发送 `Authorization` 或 `x-api-key`。
- `proxyId: null` 表示走本机直连出口；非空值必须引用现有代理。
- 管理 API 不返回 key 原文，只返回是否存在和短指纹。
- Worker 的运行期 `ready`、冷却剩余、连续失败次数和最近失败类别来自服务进程，不是静态配置字段。

### 6.3 代理与订阅

代理记录连接信息、协议类型、启用状态、来源和最近实测公网 IP。代理必须至少支持直连或 Clash 桥接之一。

- `http`、`https`、`socks4`、`socks5` 可直接建立出口连接。
- 其他协议通过本机 Clash 桥接；实际连接地址来自所选内核的 `localProxyHost`/`localProxyPort`。代理记录的 `host`/`port` 仍描述原节点，不用于选择本机混合端口。
- `egressIp` 只接受合法 IP 字面量；`null` 表示尚未成功测量。
- 订阅 URL 被视为凭证，展示和错误信息中必须脱敏。
- 订阅刷新按多个 User-Agent 尝试拉取，解析支持 Clash YAML/JSON、SIP008、分享链列表和多层 Base64；刷新结果按订阅 id 与节点名幂等合并。
- 已被 Worker 使用但已从订阅消失的代理不能自动删除；否则引用完整性会被破坏。

### 6.4 Clash

`clash` 可配置多个 Controller。每个内核包含 Controller 地址、secret、本地代理端口和 selector 分组。

- `manual` 严格使用 `activeBridgeId`；不会因探活失败而悄悄换内核。
- `auto` 可在批量探测前探活并择优，但转发过程仍按当前选中的内核工作。
- 只能桥接的启用代理要求 `clash.enabled` 为真。
- `setup` 只探测本机回环 Controller，发现混合端口、selector 和可用节点后合并进配置；它保留既有 Worker 和用户明确停用的内核。

### 6.5 模型与调度

- `models.freeSuffix` 定义免费后缀，`extraFreeIds` 保存无后缀的显式免费模型。
- `enforceCatalog` 开启时与最近一次成功目录求交集，自动剔除已下架模型。
- `defaultSurfaces` 与 `surfaceOverrides` 只用于模型页展示协议面提示，不是转发放行闸门。
- `routing.strategy` 支持 `anonymous_first`（默认）、`authenticated_first` 和 `mixed`；字段与默认值见 [usage.md](usage.md#调度-routing)。
- 冷却按限流、鉴权（401）、禁止（403，短冷却）、传输/超时/上游错误等类别分别处理；坏请求和未知错误不冷却 Worker；目录未核验模型的 401 不归咎 Worker。
- 会话亲和和 Responses 的 `previous_response_id`/`response.id` 只保存摘要，不保存原始敏感值。

## 7. 转发面要求

### 7.1 认证与路径

客户端访问以下路径时必须以 `Authorization: Bearer` 提供 Relay Token；`/v1/messages` 与 `/messages` 另外接受 `x-api-key`。

| 客户端路径 | 协议面 | Zen 上游路径 |
| --- | --- | --- |
| `/v1/chat/completions`、`/chat/completions` | `chat` | `/chat/completions` |
| `/v1/responses`、`/responses` | `responses` | `/responses` |
| `/v1/messages`、`/messages` | `messages` | `/messages` |
| `/v1/models`、`/models` | 模型目录 | `/models` |

`/health` 不需要 Relay Token，供启停脚本和诊断使用。管理 API 通过独立的回环守卫保护。

### 7.2 请求处理顺序

转发必须按以下顺序完成：读取一次原始请求体、解析副本、免费判定、检查流式能力、选择 Worker、按候选链重试、将响应流式透传给客户端。网关不能为了判定而把原始 JSON 序列化回去。

客户端凭证头、逐跳头、来源声明头和由网关重算的头会被剥离；OpenCode 身份头会透传或补齐。认证头由选中的 Worker 重新构造；Messages 面总是发送 `anthropic-version`，只有认证 Worker 另外镜像非空 key 到 `x-api-key`，匿名 Worker 不发送该头。

### 7.3 响应与目录

- 响应体原样透传，旁路扫描 SSE 文本以识别失效推理和解析 token 用量。
- 会话绑定在调度与重试结算时指向实际承接者；完整成功流才学习 Responses 输出 id 或推理指纹。失效推理优先触发解绑；断流但未确认失效时不学习也不遗忘。
- 首次目录从未成功拉取时，模型目录端点返回 `502 upstream_unreachable`，不能伪装成空列表。
- 已有旧目录时，刷新失败继续使用最后一次成功缓存；失败后进入退避，`/v1/models` 与转发路径都不在退避期内重复请求上游。

## 8. 管理 API 要求

管理 API 仅供本机后台使用，端点清单见 [usage.md 的管理 API](usage.md#管理-api)。聚合响应和写入成功响应通过契约 schema 校验；`/api/ping` 与少数直接返回的错误响应仍由路由构造，不能把所有响应都视为经过同一 schema 闸门。`PATCH /api/config` 以严格补丁形式修改可热更新配置，成功写盘后替换进程内引用。

配置补丁当前支持：

- Gateway：`maxAttempts`、请求超时和 Relay Token（三态设置/清空/不动）；清空 Relay Token 会使完整配置校验失败，必须随后设置合法 token，不能留下空值运行。
- Models：免费后缀、显式免费名单、目录 TTL、目录交集开关。
- Workers：创建、更新、删除；更新支持类型、名称、启用状态、出口绑定和显式 key 设置/清空。

管理 API 不返回 Relay Token、Zen key、代理密码或 Clash secret 原文。管理请求体上限为 1 MiB，配置写入采用原子替换并在写入前做全量 schema 与引用校验。

## 9. 管理后台功能边界

当前后台包含六个页面：概览、网关、代理池、Worker、模型和用量，并在没有可用 Worker 时显示首启向导。

- **概览**：查看服务、Worker 池、回显出口报告和目录状态；可触发出口探测。
- **网关**：查看实际监听端口、上游地址、Relay Token 指纹和版本；编辑最多尝试的 Worker 数；按 OpenCode 1.x/2.x 复制客户端配置片段。
- **代理池**：查看代理状态、解析失败原因、回显 IP、被哪些 Worker 引用；查看回显分组；控制批量探测（启动前确认）；刷新已有订阅。
- **Worker**：新增、行内编辑（出口用代理下拉框选择）、删除（需确认）Worker；支持认证/匿名切换、启用状态、名称和出口绑定；认证 key 可设置；界面不提供单独“清空 key”，要去掉 key 需改为匿名（认证类型保留空 key 会被 schema 拒绝），切换时会清空未提交的 key。保存结果区分成功与失败。
- **模型**：查看目录中的免费与付费模型及判定原因；配置中的显式免费名单和协议面覆写也会显示，即使条目已不在当前目录。`listed` 标记当前是否在架；启用目录交集时，缺失的免费项显示为已下架，关闭交集时仍显示可用。编辑免费后缀、无后缀免费名单及目录交集开关。
- **用量**：查看请求与上游尝试、按模型和 Worker 聚合的 token、缓存命中率、用量覆盖率、未报用量和网关拒绝原因。
- **全局**：主题默认跟随系统，页头可切换跟随系统/浅色/深色；轮询失败时保留上次数据并显示过期提示；导航与页内标签是链接，可在新标签页打开；向导只在概览、Worker、网关页完整显示。

当前后台不提供代理、Clash 内核和订阅条目的完整表单 CRUD；订阅条目需要先写入配置文件，之后在后台触发刷新。后台也不提供 `defaultSurfaces` 和 `surfaceOverrides` 的编辑入口，这些字段仍需手工配置。

## 10. CLI 工作流

### 首次启动

1. 运行 `npm start`。脚本先构建；首次启动时服务会创建并校验默认配置，生成 Relay Token，再开始监听。
2. 如需 Clash 出口，先运行 `npm run setup -- --dry-run` 查看探测和合并结果，再运行 `npm run setup` 写入配置，随后立即运行 `npm run restart`；重启前不要在后台保存配置（见 [usage.md](usage.md#导入-clash-出口)）。
3. 在后台新增认证或匿名 Worker，或按提示编辑数据目录中的 `config.json`。
4. 若手工修改了配置文件，运行 `npm run restart`；后台提交的 Worker 修改即时生效。再运行 `npm run doctor` 检查配置、服务、数据库、Worker、Clash 和目录。
5. 在客户端把本地 `/v1` 地址和配置文件中的 Relay Token 填入客户端 provider 配置。

### 日常排查

- `npm run status` 只检查服务进程、PID、端口和健康状态，不显示调度器细节。
- `npm run doctor` 按依赖顺序只报告第一个失败层，并给出下一步；它默认不修改配置和数据库。
- `npm run doctor -- --deep` 额外对 IP 回显目标发请求并切换 Clash selector；运行结束后
  selector 可能停在最后一次探测的节点。
- `npm run discover:upstream` 需要网络，用于手工重验上游行为，不属于本地验证关卡。
- `npm run validate` 执行类型检查、双构建和全部测试，构建必须先于测试。

## 11. 可验收功能

以下条件可作为功能验收清单：

1. 网关启动后 `/health` 返回健康结构，服务端只监听回环地址，非法配置不会启动。
2. 未携带或携带错误 Relay Token 的转发请求被拒绝；管理 API 从非回环来源访问被拒绝。
3. 三个协议面的有前缀和无前缀路径均经过同一套鉴权、免费判定、调度、重试和透传流程。
   真实 CLI 验收的方法见 [usage.md 的客户端验收](usage.md#客户端验收)，范围见 §13。
4. 客户端原始请求字节与上游收到的请求体保持一致；网关解析副本不会改变转发内容。
5. 在目录可用且启用 `enforceCatalog` 时，符合免费约定但已下架的模型在本机被拒绝；不符合免费规则的模型始终在本机拒绝。目录不可用或关闭交集时，网关只按后缀/名单放行，最终由上游处理目录差异；所有网关自身拒绝都在统计中记录原因。
6. 认证 Worker 发送其自身 key，匿名 Worker 不发送认证头；客户端传入的凭证头不会覆盖网关决定。
7. Worker 冷却、候选排序、最大尝试次数和实际承接者亲和绑定符合配置与错误分类。
8. 流式响应在上游断流、失效推理和正常结束三种结局下分别执行正确的解绑、学习和统计动作。
9. `/v1/models` 在目录从未成功取得时返回 502；已有旧缓存时刷新失败不会清空缓存。
10. 出口探测成功后，代理或本机直连访问 IP 回显目标的实测公网 IP 写回配置；报告按 IP 分组，未探测项不计为独立。
11. 配置补丁支持 Worker 创建、编辑、删除和凭证三态语义；写盘失败时进程内配置不半生效。
12. 订阅刷新可重复执行而不产生重复节点，失败状态可在后台看到，仍被 Worker 使用的旧节点不会被删除。
13. 批量探测由服务端持有进度，同一时刻不能启动两批，并支持暂停、继续和取消。
14. 管理后台不显示任何凭证原文；页面能区分服务未连接、响应异常、目录不可达、Worker 冷却和出口未探测。
15. 用量页区分客户端请求与上游尝试、上游未报告用量与网关未完整解析用量。

## 12. 当前已完成范围

- 本机回环服务、Relay Token 鉴权、三种协议面、模型目录代理和免费模型判定已接通。
- Worker 的认证/匿名类型、出口绑定、运行期状态、冷却和亲和调度已接通。
- 直连和 Clash 桥接两类出口、多个 Clash 内核、回显出口实测和分组报告已接通。
- 配置严格校验、热更新补丁、凭证脱敏、原子写盘和运行时数据库统计已接通。
- 管理 API、六页管理后台、首启向导、批量探测状态机和订阅刷新已接通。
- `setup` 可发现本机 Clash Controller 并导入其可用节点；`doctor` 可按层诊断并在深度模式下实测 IP 回显目标。

## 13. 当前未实现或需要外部配合的范围

- 生产环境的后台静态文件托管不由网关负责，需要单独的静态服务器或开发环境中的 Vite。
- 代理、Clash 内核和订阅的完整编辑界面尚未提供；仍需手工编辑配置或运行命令行工具。
- `defaultSurfaces` 和 `surfaceOverrides` 不在配置补丁 schema 中，没有后台入口，只能手工编辑配置文件后重启。
- `gateway.headersTimeoutMs`、`gateway.bodyTimeoutMs` 和 `gateway.relayToken` 可通过 `PATCH /api/config` 修改，但后台没有对应表单。
- `routing` 整节不在配置补丁 schema 中，只能手工编辑配置文件后重启。
- 新的无后缀免费模型需要人工确认后加入名单；上游目录本身不提供价格信息。
- 匿名 Worker 是否可用取决于 Zen 上游的实际认证策略，网关不会替上游承诺匿名访问成功。
- 当前免费模型的真实 CLI 验收覆盖 Chat Completions 与 Responses，模型是否成功仍
  受出口地域和上游当时策略影响，某次出口样本不能推广为固定可用性。Messages 的
  路由、鉴权、原样透传和流式处理已完成本地协议级验证，但当前没有可验的免费 Zen
  上游模型，待上游提供后再做真实验收。
- Clash 的运行期故障切换、远程管理、多用户鉴权和跨机器部署均不在当前范围内。
- 上游网络、企业 CA、DNS、代理环境和账号权限属于本机/外部环境；`doctor` 只能报告检测到的症状，不能替用户修复这些外部条件。
